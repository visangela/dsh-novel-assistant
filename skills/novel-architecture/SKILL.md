# 阶段 1 · 小说架构

目标：把模糊的灵感变成一份可执行、可查证的架构，外加 3–6 个主要人物的小传。**本阶段不写故事大纲。**

前置：读 `novel-project/PROJECT.md` 和 `bible/architecture.md`；如果项目还没建，先走 `novel-setup`。

## 一、从想法里提取五件事

用户给的想法可能只有一句话。先在心里拆出：

1. **谁**：主角是什么人，现在过着什么日子。
2. **想要什么**：他主动追求的目标。
3. **被什么挡住**：最直接、最具体的阻力。
4. **代价**：他为这件事愿意失去什么。
5. **特别之处**：这本书区别于同类的地方（金手指、规则、关系、视角）。

把提取结果用 4–6 行复述给用户：「我听到的是……对吗？哪里不对？」**先对齐，再设计。**

## 二、参考作品的处理（用户点名要参考时）

用户说「参考《XXX》」时，不要拒绝，也不要照搬。做四层拆解，并明确告诉用户你借的是哪一层：

| 层 | 可以借 | 不可以借 |
| --- | --- | --- |
| 世界规则 | 力量体系的组织方式、社会结构的功能位 | 专有名词、门派/家族/地名的原样复制 |
| 关系张力 | 人物关系的功能组合（如「互相利用的师徒」） | 具体人物的姓名、身世、标志性情节 |
| 节奏机制 | 爽点/悬念的投放方式、卷末高潮的结构 | 逐章情节、名场面复刻 |
| 母题气质 | 主题、意象系统、情绪基调 | 原文句子、独创设定 |

操作要求：

1. 先列出「借鉴清单」与「禁区清单」，让用户确认边界。
2. 做**至少两处结构性替换**：换舞台、换代价、换关系走向，确保不是换皮。
3. 在 `architecture.md` 的「参考作品与借鉴边界」里写清借了什么、不借什么。

如果用户要的是「像某某作者的文风」，那是阶段 2 的事，转 `novel-style`，不要在架构阶段处理。

## 三、架构访谈（每次 3 个问题，最多三轮）

按下面的顺序问，用户已有答案的跳过：

**第一轮：世界与规则**

1. 故事发生在什么时代、什么舞台？有没有超凡力量（修炼 / 异能 / 系统 / 无异能）？
2. 这个世界最不公平的一条规则是什么？（冲突的源头）
3. 主角的「金手指」是什么？它的代价和限制是什么？（没有代价的能力不能要）

**第二轮：人物与关系**

4. 主角最想要什么？为什么现在得不到？
5. 谁最爱他、谁最恨他、谁最懂他？这三个人分别想要什么？
6. 主角最大的性格缺陷是什么？这个缺陷会让他付出什么代价？

**第三轮：矛盾与结局倾向**

7. 全书最核心的矛盾是什么？（谁与谁、争什么、为什么不能让）
8. 你希望结局偏向哪种：赢回一切 / 惨胜 / 失去后释然 / 开放式？
9. 有没有绝对不能写的内容（雷点、尺度、BE/HE）？

规则：

- 用 `ask_user_question`，给选项 + 推荐项；开放题才让用户自由输入。
- 用户答「不知道」时，给 2–3 个具体选项并说明各自的故事后果，让用户选一个，而不是替用户定。
- 每轮结束把已确认的设定复述一遍，再问下一轮。

## 四、写 `bible/architecture.md`

按模板逐项填满，不许留空。重点检查：

- **金手指三件套**：能力、代价、成长曲线。三者缺一，后面一定写崩。
- **反派逻辑**：反派必须有一个「他自己认为正确」的理由；写不出就说明反派是纸片人。
- **主角动机**：主角的目标要具体到「今晚要拿到什么」，不能是「变强」。
- **情感关系**：至少一条关系有「既需要又对抗」的张力。

写完后做一次自检，把发现的问题列给用户，不要自己偷偷改。

## 五、写人物小传

为主要人物（主角、对手、爱人/挚友、关键长辈或引路人，3–6 人）各写一份 `bible/characters/<拼音或英文名>.md`，用 `bible/characters/_template.md` 的结构。

硬性要求：

- **成长经历**必须能解释他现在的执念；不能是流水账。
- **执念**要写到「为此愿意放弃什么」，否则人物没有重量。
- **能力体系**要写上限与代价，和主角金手指的规则一致。
- **说话方式**要具体到句长、用词、口头禅、回避的话题，并给一句代表性台词；这是后面对话区分度的依据。
- **人物弧光**写清起点、关键选择、终点，以及「哪件事必须发生」弧光才成立。

同时更新 `bible/characters/_index.md` 的人物表。

## 六、可选：一次「吸引力评审」

架构写完后，可以用 `subagent` 开 2–3 个不同读者视角（例如「只看前三章的追更读者」「挑逻辑漏洞的老书虫」「负责改编的编辑」），让它们只读 `architecture.md` 与人物小传，回答：

- 这个设定最吸引人的点是什么？
- 最可能劝退读者的点是什么？
- 哪个设定自相矛盾或过于便利？

把评审意见汇总成 3–5 条，交给用户决定改不改。评审子任务只读不写，避免多人同时改文件。

## 七、收尾汇报与门禁

汇报控制在 10 行以内：

- 产出的文件路径；
- 一句话世界观 + 一句话主线矛盾；
- 主角的金手指与代价；
- 主要人物一句话一个；
- 自检发现的风险（若有）；
- 待用户确认的 1–3 个点。

然后问：「架构就按这版定，还是先改哪一块？」选项：定稿，进入风格 / 改世界观 / 改人物 / 我再想想。

用户确认后更新 `PROJECT.md`（阶段改为 2、记录决策），加载 `novel-style`。**未确认不要进入下一阶段。**
