# 阶段 8 · 快速检查

目标：在错误扩散到后面十章之前抓住它。**本阶段只诊断、只小修；不重写整章，不擅自改大纲。**

## 一、触发与范围

开场先跑一次 `node "<技能 Base directory>/../novel-graph/tools/graph-sync.mjs" --project novel-project --check`：它会指出已写章节里还没打强度分的章、没登记小传的人物、关系表缺行。这些不是正文问题，但会让图谱停在旧版，顺手记进报告「图谱同步」一节。

- 主动触发：`novel-draft` 每写完 1–3 章，主动加载本技能，范围 = 最近这 1–3 章。
- 被动触发：用户点名章节（「看看第 12 到 14 章」），范围按用户说的；没说就取最近 3 章。
- 范围锁定后先写下来：「本次检查 ch012–ch014，共 3 章，约 9000 字」。范围外的发现单独记「越界发现」，不混进本次结论。
- 开场先跑一次改稿体检：`node "<novel-draft 技能目录>/tools/reconcile-chapter.mjs" --all --project novel-project`。有「改过、还没核对」的章，先并进本次范围（改过的地方最容易出逻辑洞）；有「没有存档」的章，检查通过后补 `--archive`；有「设定库要跟上」的章，把清单里的事实改动逐条比对本卷正文，看有没有被漏掉的连带修改。

## 二、先读什么

| 文件 | 读它来判断 |
| --- | --- |
| `novel-project/chapters/vol-XX/ch-YYY.md` | 本批正文，逐章通读，至少一遍 |
| `novel-project/bible/outline.md` | 主线、分卷、章节关键设定表（判断漂移的基准） |
| `novel-project/outline/vol-XX/ch-YYY.md` | 本批细纲：计划事件、冲突、埋设/回收 |
| `novel-project/bible/timeline.md` | 故事时间、地点、路程、伤势 |
| `novel-project/bible/facts.md` | 度量、账目、纪年、器物规格等可核对事实 |
| `novel-project/bible/digest.md` | 每章一行摘要；核对「摘要说的」与「正文写的」是否一致 |
| `novel-project/reviews/draft-edits/*.md` | 近期改稿清单：哪些段被改过、新出现哪些数字/伏笔/人物（判断「账本是否跟进」） |
| `novel-project/bible/foreshadowing.md` | 已有伏笔编号、预定回收章、状态 |
| `novel-project/bible/knowledge-reader.md`、`knowledge-protagonist.md` | 信息差计划 |
| `novel-project/bible/characters/_index.md` 与相关小传 | 说话方式、执念、能力上限 |
| `novel-project/bible/style.md` | 句式、视角、禁忌（判断文风跑偏） |

读不到的文件不要跳过检查项，改为「按正文反推 + 在报告里标注设定库缺失」。

补一条：**先跑 `plot-check.mjs`**，把它吐的「平线 / 掉速 / 断钩」当作第 9 项的原料，而不是自己想「节奏好像有点慢」。

## 三、九项检查（逐项给证据）

每一处问题都必须写成：**章节 + ≤30 字原文短引 + 为什么是问题**。没有原文证据的，不许写进问题表。

数字、度量、纪年这类**可核对事实**，一律以 `facts.md` 为准：正文里的数算不出表里的结果、或前后两章用了两套口径，都算问题，不要凭常识放过。

1. **逻辑与因果**
   问三次「他为什么这么做」：动机在正文里有没有落点？有没有为了推情节让人物降智、突然信任、突然暴怒？前因是不是靠旁白补的（「其实他早就知道」）？动机只在小传里、正文没写，也算问题。

2. **时间线**
   对照 `timeline.md` 核：路程耗时、伤势恢复、昼夜与季节、人物是否同时出现在两地、信使与消息传播速度。特别注意「次日」「三日后」「半个月后」这类词有没有和表里冲突；本章开头和上一章结尾是否接得上。

3. **人物一致性**
   对照小传的「说话方式」：句长、用词、口头禅、回避的话题是否跑偏；行为是否违背执念与能力上限。判断 OOC 的标准不是「我觉得不像」，而是「小传里写的哪一条被违反了」。配角是否只在需要时出现、说完功能台词就消失。

4. **信息差**
   拿两张表对正文：读者现在知道了什么、主角知道了什么，是否与计划同步。检查三种泄漏：读者表里没有的信息被正文直接说明（提前泄底）、主角知道了不该知道的事、本该由读者知道而正文没给（悬念断线）。

5. **伏笔账本**
   本批新埋的伏笔有没有登记进 `foreshadowing.md`（编号、埋设章、指向真相、预定回收章）；到期未收的标「逾期」；已回收的更新状态。回收时是否真的解释了「指向的真相」，还是只提了一句就过。

6. **节奏**
   看这批章的冲突曲线：有没有连续 3 章没有冲突升级（平淡）、或连续高压没有呼吸段。每章章末有没有钩子（悬念、反转、决定、坏消息），钩子是不是同一类型连用。信息密度：有没有整章只有对话没有推进。

7. **重复与 AI 味**（这里的「AI 味」指文本里的机械感，不是检测工具）
   重复句式（连续主谓宾、每段同结构）、口头禅滥用（「不知过了多久」「空气仿佛凝固」「与此同时」）、总结式抒情（「这一刻，她终于明白……」）、每段都收在哲理句、情绪标签代替动作（「她感到很悲伤」）。用 `grep` 统计可疑短语出现次数，给出次数与位置。

8. **大纲漂移**
   把正文实际发生的事，逐条对 `outline.md` 的「章节关键设定」与细纲。偏离分两类：**增益性偏离**（正文比大纲更好，建议回写大纲）与**破坏性偏离**（动了因果、人物动机、主线节点，必须处理）。不要把所有偏离都当错误。

9. **节奏曲线（机器自检，先跑再看）**
   跑一次：

   ```bash
   node "<技能 Base directory>/../novel-graph/tools/plot-check.mjs" --project novel-project
   ```

   它只查三种形状，不评价文字好坏：

   | 形状 | 含义 | 怎么处理 |
   | --- | --- | --- |
   | 平线：同一条线连续 3 章同一个值 | 这条线三章没推进 | 要么承认它是刻意低烧、在细纲注明；要么给出下一章的推进点 |
   | 掉速：前一章 ≥4、下一章掉 ≥2 分 | 该爆的地方写软了 | 回看那一章是不是被别的线挤掉、冲突被提前花掉 |
   | 断钩：伏笔埋下后两章内主线跌到 ≤1 | 埋了没接 | 下一章必须接上，或把埋点后移 |

   把命中的每一条**原样抄进问题表**，严重度默认「提示」——曲线是形状，不是判词；平线可能是刻意铺垫，掉速也可能是换线叙述。只有当这一条与第 6 项（节奏）的阅读感受一致时，才升为 high。

## 四、产出 `reviews/quick-check-chXXX-YYY.md`

文件名用实际章号，例如 `novel-project/reviews/quick-check-ch012-014.md`。结构固定：

```markdown
# 快速检查 ch012–ch014

- 检查范围：ch012–ch014（约 9,200 字）
- 检查日期：YYYY-MM-DD
- 结论：可继续 / 建议小修 / 需要动大纲

## 一、问题表

| 编号 | 严重度 | 位置 | 证据（短引） | 为什么是问题 | 修法（含代价） |
| --- | --- | --- | --- | --- | --- |
| Q1 | blocker | ch013 第 4 段 | 「他早知密道」 | 主角第 9 章才拿到地图，此处越权知情 | A 改对话让他猜（+1 段）；B 删这句（-20 字，失去悬念）；C 提前给地图（要改 ch009） |

## 二、不需要改的确认项

- ch012 的雨夜赶路与 timeline 第 7 日吻合，保留。
- 沈砚秋的三次短句回答符合小传，不要为了「自然」加长。

## 三、伏笔账本变动

| 编号 | 变动 | 说明 |
| --- | --- | --- |
| F007 | 新增 | ch013 茶盏裂纹，预定 ch041 回收 |

## 四、接下来 1–3 章的写作指导

- 保留：……
- 改：……
- 下一章必须注意：……
```

严重度用 `blocker`（读者会看不懂或设定自相矛盾）、`high`（明显出戏）、`medium`（读起来钝）、`low`（风格偏好）。每条修法给 2–3 个并写清代价（字数、要动的章、失去的效果），不要只给一个「改好一点」。

## 五、先给结论，再问用户

结论只有三档，先一句话说清：

| 结论 | 判据 | 建议动作 |
| --- | --- | --- |
| 可继续 | 只有 low，或 medium 且不影响后续 | 记入报告，继续写 |
| 建议小修 | 有 high，但不动主线 | 修 1–3 处再继续 |
| 需要动大纲 | 有 blocker，或破坏性偏离 | 走下面的联动流程 |

然后用 `ask_user_question` 一次问完（最多 3 问）：

1. **「大纲线要不要调整？」** 选项：不动（默认推荐，问题都在句内）/ 小改（局部事件替换，影响 1–3 章）/ 大改（改主线或结局，影响后续全部）。
2. **「这次修到什么程度？」** 选项：只修 blocker 与 high（推荐）/ 全修 / 先记账、接着往下写。
3. **「已发布章节要不要回改？」** 选项：不回改、在后续章节里圆（推荐）/ 回改并在 `PROJECT.md` 记「已回改」/ 只改硬伤句。

**不要替用户决定改大纲。** 用户选「不动」而报告里写着需要动大纲时，把这个矛盾明确说出来，让他再确认一次。

## 六、用户决定改大纲时：按顺序联动

先列「联动清单」给用户看（改哪条、牵动哪些文件、预计影响几章），确认后按这个顺序执行，**不要跳步**：

1. `bible/outline.md`：主线 / 分卷表 / 章节关键设定表。
2. 受影响的细纲：`outline/vol-XX/ch-YYY.md`，当前章与后续 3–5 章。
3. 设定库：`timeline.md`、`foreshadowing.md`、`knowledge-reader.md`、`knowledge-protagonist.md`、相关 `characters/*.md`。
4. 后续章节计划：下一批细纲要改的条目、卷末高潮是否位移。
5. `PROJECT.md` 决策日志：日期 + 改了什么 + 为什么 + 影响章范围。
6. 已发布章节回改：由用户决定；回改后在 `PROJECT.md` 记明章号。

改完做一次复查：新大纲与 `timeline.md` 是否自洽、被删伏笔是否还有悬空引用（`grep` 伏笔编号）、受影响章节的细纲是否都改了。复查结果写进报告末尾。

## 七、必须落到「接下来 1–3 章的写作指导」

检查报告不是终点。最后写三条，具体到可执行：

- **保留什么**：已经成立的东西，明确写「不要在下一章自我否定」。
- **改什么**：后续章节必须体现的修正，写到章号与场景。
- **下一章要注意什么**：1–3 条禁令，例如「ch015 之前不要提密道」「不要让陆沉主动示好，他的转变在 ch019」。

## 八、质量自检清单（逐条打勾）

- [ ] 八项每项都有结论，「无问题」也要写一句为什么无问题。
- [ ] 每条问题都有章节 + 原文短引；没有凭印象的判断。
- [ ] 每条问题至少 2 个修法，并写了代价。
- [ ] 时间线冲突是对照 `timeline.md` 得出的，不是凭记忆。
- [ ] 新埋伏笔已登记，逾期伏笔已标状态，回收状态已更新。
- [ ] AI 味问题给了出现次数或位置，不是笼统说「有点 AI」。
- [ ] 大纲漂移区分了增益性与破坏性。
- [ ] 没有擅自修改 `outline.md`。
- [ ] 报告已落盘，`PROJECT.md` 与结论一致。

## 九、门禁

用户确认检查结论与调整方案（含「不动大纲」）后：

1. 若改了大纲，先确认联动清单六步都完成并复查通过；
2. 更新 `PROJECT.md`：最近检查章、遗留问题数、下一步；
3. 回到 `novel-draft` 继续写。

**未确认不要继续写下一章。**

## 十、失败与回退

| 情况 | 处理 |
| --- | --- |
| 章节文件缺失或编号跳号 | 用 `glob` 列实际文件，按实际章号命名报告；在报告里标「编号不连续」 |
| `bible/` 为空或没建档 | 从正文反推最小 `timeline` / `foreshadowing` 条目补上，报告标「按正文回填，请确认」 |
| 用户只查某一项（「只查时间线」） | 只跑该项，报告里列「未检查项」，别假装全查过 |
| 问题超出本批范围（人物动机已崩） | 升级到 `novel-mid-check`，或回 `novel-architecture` 修人物；不要在快速检查里硬改 |
| 用户要求「你直接改完」 | 先给修改清单与代价，改 blocker 与 high；整章重写不在本技能范围，转 `novel-draft` |

## 十一、收尾

汇报不超过 10 行：检查范围、结论、问题数量按严重度分布、报告路径、问了哪 3 个问题与用户选择、接下来写哪几章。然后加载 `novel-draft`；若结论是「需要动大纲」且用户已确认大改，先回 `novel-workflow` 重新对阶段，再进 `novel-detailed-outline`。
