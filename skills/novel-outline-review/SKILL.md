# 阶段 4 · 大纲审核

目标：在写细纲之前，用外部视角找出会让读者弃书、或让后文写崩的问题。**只诊断、只给修法，不直接改 `bible/`。** 改不改由用户决定，改动由阶段 1–3 的技能执行。

## 一、前置检查

- `bible/outline.md` 六节都有实质内容，不是模板占位。
- `bible/architecture.md`、`bible/style.md`、`bible/characters/*` 可读。
- 没有大纲 → 回 `novel-outline`；架构与大纲明显矛盾 → 先记下，作为本次的一条 finding，不要当场改。

## 二、开评审子任务（推荐做法）

用 `subagent` 并行开 4–5 个视角，一个视角一个子任务。先 `list_subagent_models` 看可用模型；审核类任务选低温、强推理模型，`reasoning_effort` 用 high。

每个子任务的提示必须写清四件事：

1. **只读这些文件**：`bible/outline.md` + 该视角需要的（逻辑编辑加 `architecture.md`，人物弧光编辑加 `characters/*`，类型读者加 `PROJECT.md` 的题材与读者）。
2. **不许改任何文件**，不许写 `reviews/`，不要提修法之外的执行动作。
3. **输出格式固定**（见下），最多 5 条，按严重度排序；没有问题就写「无」。
4. **每条必须指出具体位置**（第几卷 / 第几章 / 哪一节），不许说「整体感觉」「略显平淡」。

| 视角 | 只回答的问题 |
| --- | --- |
| 追更读者 | 哪一段我会弃书？哪里让我想追下一章？哪个角色我喜欢不起来？ |
| 逻辑编辑 | 谁的动机不成立？哪条因果链断了？金手指是否过强？ |
| 人物弧光编辑 | 主角每卷有没有变化？配角是否只承担功能？感情线有没有阻碍？ |
| 节奏编辑 | 哪几章连续平淡？高潮间隔多长？中点够不够强？ |
| 类型读者 | 作为古言 / 仙侠 / 悬疑读者，哪些套路用错了？类型承诺有没有兑现？ |

子任务输出格式（固定，便于汇总去重）：

```
位置：卷二 第 7 章 / 第三节 分卷表
问题：一句话
为什么：读者会怎么想 / 后文会在哪里崩
建议：一条可执行的改法
严重度：blocker | high | medium | low
```

没有 `subagent` 能力时：按同样五个视角顺序做 5 轮自审，每轮只戴一个视角的帽子、只回答该视角的问题，不要混着看。报告开头注明「本次为单模型分轮自审，非独立多角色评审」，并降低对「吸引力」类结论的置信度。

## 三、固定检查清单（17 项，逐项给结论）

| # | 检查项 | 判定（通过 / 风险 / 不通过） | 证据位置 |
| --- | --- | --- | --- |
| 1 | 主角目标是否具体 | | |
| 2 | 反派是否可信（他自己的理由能否成立） | | |
| 3 | 金手指是否过强（有代价、有解不了的局） | | |
| 4 | 结局是否被前置铺垫 | | |
| 5 | 每卷是否有独立目标 | | |
| 6 | 冲突是否逐卷升级 | | |
| 7 | 是否有重复事件（同类冲突用两次以上） | | |
| 8 | 是否有连续平淡段（连续 3 章无变化） | | |
| 9 | 人物动机是否前后一致（尤其反派与爱人） | | |
| 10 | 感情线是否有阻碍 | | |
| 11 | 伏笔是否有回收计划 | | |
| 12 | 时间线是否自洽（赶路 / 养伤 / 节庆 / 年龄） | | |
| 13 | 世界观规则是否被违反（力量体系 / 社会规则） | | |
| 14 | 章节表是否有水章（删掉不影响后文） | | |
| 15 | 开篇三章是否抓人（第 1 章有异常与欲望） | | |
| 16 | 中点是否改写规则（旧方法是否失效） | | |
| 17 | 主角是否始终主动（关键转折是否靠别人救） | | |

每项都要落到具体位置，写不出位置说明这项没查清，不算通过。

## 四、汇总去重与分级

1. 合并同一问题的多个视角意见，保留最具体的证据；同一位置的多条意见合成一条。
2. 按 blocker > high > medium > low 排序。分级标准：
   - **blocker**：不改会导致主线断裂、结局不成立、读者必然弃书。
   - **high**：明显削弱吸引力或可信度，但不影响主线成立。
   - **medium**：局部问题，可在细纲阶段顺手修正。
   - **low**：风格偏好，可改可不改。
3. 每条给 2–3 个修法，并标代价：

| 修法类型 | 代价 |
| --- | --- |
| 改设定 | 最大，连带改人物能力、世界观、后续卷 |
| 改事件 | 中等，改一章或一段节拍，注意伏笔回收 |
| 改顺序 | 最小，挪章 / 换视角，但会影响节奏曲线 |

4. 标影响面：「改这条 → 需要同步改 X（人物）、Y（伏笔）、Z（第几卷）」。影响面超过三处的，提醒用户这是一次结构性改动。

## 五、写报告

产出 `novel-project/reviews/outline-review-v1.md`，结构固定：

```
# 大纲审核报告 v1
- 审核对象：outline.md（版本 / 日期）
- 评审方式：多角色 subagent / 单模型分轮自审
- 结论：可进入细纲 / 需修改后复审

## 必须改（blocker）
（每条：位置、问题、为什么、修法与代价、影响面）

## 建议改（high / medium）
## 可以不改（low）
## 检查清单结果（17 项）
## 与上一版对比（v2 起）
```

复审写 `outline-review-v2.md`，开头加一段「上版问题关闭情况」：逐条标 **已关闭 / 部分关闭 / 未处理**，未处理的写原因。不要重写整份报告掩盖历史，用户需要看到问题是怎么收敛的。

**报告自检（4 条，缺一项就补）**：每条 finding 都有具体位置；每条都写了「不改会怎样」；每条修法都标了类型与代价；blocker 数量与「结论」一栏一致。

## 六、用户交互点

汇报时不要一次抛 20 条。按三组说，每组先给数量与最严重的一条：

1. **必须改（blocker）**：不改会怎样崩，说清具体后果。
2. **建议改（high / medium）**：给「改 / 不改 / 留到细纲再看」三个选项，推荐「先改影响主线的那几条，其余留到细纲」，并说明留到细纲的返工风险。
3. **可以不改（low）**：一句话带过，不展开。

用 `ask_user_question` 让用户逐组决定，最多 3 问。用户选择修改时，按问题归属回到对应技能：

- 设定、人物、金手指问题 → `novel-architecture`
- 文风、叙述视角问题 → `novel-style`
- 结构、节奏、章节表问题 → `novel-outline`

改完**不要直接进下一阶段**，回到本技能复审（v2）。

## 七、门禁

- blocker 清零：每条都有明确处理结论（已改 / 用户决定接受并记录理由）。
- 用户明确说「可以进入设定库」。
- 更新 `PROJECT.md`：阶段 4 → 5、审核版本、blocker 处理结果、决策日志记一行。
- 然后加载 `novel-bible`（阶段 5）。**有 blocker 未关闭时不得进入阶段 5。**

## 八、失败 / 回退分支

- **大纲太粗无法审**：先回 `novel-outline` 补卷级节拍，不要在审核里替用户编情节。
- **评审意见互相冲突**：不要投票决定。把冲突双方的理由与代价并列给用户，说明选每一边会牺牲什么。
- **用户不接受任何 blocker**：记录「用户已知风险并接受」，在 `PROJECT.md` 留痕后放行；但报告里要写清后续最可能崩在哪一卷、崩在哪个事件。
- **subagent 不可用或超时**：降级为分轮自审并注明，不要因此跳过审核；仍要出报告与清单。
- **复审仍剩 blocker**：不要为了过门禁把 blocker 降级。列清未解决项，给用户两个选项——继续改，或明确接受风险后进入阶段 5。
