# 阶段 7 · 正文

目标：把细纲写成**能读的正文**，单章 2000–4000 字（以 `PROJECT.md` 的设定为准，默认 3000）。一次写一章：开写前读够，写完自检，交用户确认，再写下一章。不要在对话里贴整章草稿，落盘后再汇报。

## 零、这一章由谁写（先读 `PROJECT.md` 的「正文模型」块）

三种通道，选一个执行，**不要每章追问用户**：

| 通道 | 执行者 | 默认 | 何时用 |
| --- | --- | --- | --- |
| L3 主代理自写 | 你自己 | 是 | 没写「正文模型」，或代笔模型不可用 |
| L1 自动代笔 | `subagent` + 指定 provider/model | 关 | 用户把正文模型定成了别的模型 |
| L2 手动代笔 | 用户在外部工具写，贴回来 | 关 | 用户说「这一章我自己写」或想拿别的工具试 |

读不到这一块 → 按 L3 走，汇报时顺带提一句「要不要把正文模型固定下来」，**别每章问一次**。

### 首章试笔（B 档：双段同写，一本书只做一次）

`PROJECT.md` 的「正文模型」块写着「选择方式：试笔」，且 `chapters/` 还是空的 —— 先做完这一步，再写正式第 1 章。目的不是选出「更强的模型」，是让用户**看着样章做决定**，而不是听描述做决定。

1. 用 `<技能 Base directory>/templates/draft-trial.md` 填试笔单。两段同题：**段一**取第 1 章细纲「冲突与推进」第 1–2 段（开场钩子），**段二**取第 3–4 段前半（纯执行的中段推进）。各 700–900 字，都写清「写到哪停」，否则两家停的位置不同，没法比。
2. 你写 L3 两份：`reviews/draft-trial/L3-opening.md`、`L3-scene.md`。
3. 跑 `context-pack.mjs 1`，把输出贴进试笔单；调 `subagent` 写 L1 两份（`L1-opening.md`、`L1-scene.md`）。**必须要求它自己 read `style.md` 全文**，别只给摘要——摘要管得住引号和句长，管不住段落密度（实测段均差 13 字）。
4. 试笔稿**不跑 `check-chapter.mjs`**：它不是章节，没有「# 第 N 章」标题，跑了只会报 title 错误。用第四节清单 + 你自己读。
5. 收到 L1 稿先过三条硬线，过不了**退回重写一次**，说清差多少（字数、占比、停在哪）：字数 700–900 汉字（用 `check-chapter.mjs --min 700 --max 900` 的数字口径数，别目测）/ 对话占比 35%–45% / 必须停在试笔单写的那个位置。返回值只退回，不替它补写——补写出来的就不是它的笔了。
6. 给一页对比：字数 / 段均 / 最长段 / 对话占比 / 物象数 / 违反第八节禁忌几处 / **三条读感差异，每条指到具体句子**。不要写「B 更有感染力」这种空话。
7. `ask_user_question` 让用户二选一（L1 还是 L3），选项里带推荐与理由；用户说都不满意，就按他的意见改试笔单再来一轮，别自己判定。
8. 结果写进 `PROJECT.md`：通道、代笔模型（选 L1 时）、选择方式改「已定」、试笔日期与选中理由一行。没选中的那一路留在 `reviews/draft-trial/` **不删**——用户以后想反悔，得有东西可看。
9. 接着写正式第 1 章。允许把选中的那两段接续扩写，但要重新过第一节必读、落盘校验、写摘要行，**试笔稿不是正文**。

试笔跑不起来（没定代笔模型、路由没放行、`list_subagent_models` 报错）：**不要卡住第一章**。按 L3 写，汇报里说清「这次没试笔，因为 X」，`PROJECT.md` 的选择方式改「跟随默认」，等用户想试了再补。

### L3 主代理自写（基准）

就是下面第一节到第十一节的完整流程。这条是基准线：代笔省的是时间，不是标准。

### L1 自动代笔（子代理写，你审）

前提：`PROJECT.md` 写明代笔模型，且 `list_subagent_models({ provider, model })` 不报错。

报 `LLM provider "X" is not allowed for this Session` 时**不要重试、不要偷偷换成能用的模型**：改走 L3，并告诉用户：「Host 的『插件 → 子智能体 → 模型选择』没放行这条路由，改完要新开会话才生效。」

步骤：

1. 你自己按第一节 7 条读一遍设定。**审稿的人必须先懂稿**，不能只当传声筒。
2. 先跑一次上下文打包，别自己翻正文：
   ```bash
   node "<技能 Base directory>/tools/context-pack.mjs" <章号> --project novel-project
   ```
   输出里有细纲点名的伏笔原句、最近三章摘要、上一章末尾。把整段贴进交接单的「附录：上下文包」——**代笔模型看不到这个项目，它只能看到你贴的东西**。脚本报「没在正文里找到这个物象」就别含糊带过，先回那一段确认伏笔表写的是不是正文真写过的。
3. 用 `<技能 Base directory>/templates/draft-brief.md` 填好交接单，调 `subagent`：`provider` / `model` 取自 `PROJECT.md`，`description` 写「第 N 章正文」。提示词必须给全：读哪些文件、写到哪个路径、硬约束、验收标准。**交接单的「输出格式」要用 L1 版**（它自己落盘并写账本注释），别把 L2 的「只输出正文」发给它。
   `reasoning_effort` **先查再传**：`list_subagent_models({ provider, model })` 看这条路由声明了哪些档位，只传它支持的；拿不准就整个省略，用模型默认。分层路由（例如 `Gemini 4 Argon (Low)`）档位已经写进模型名，再传 `medium` 会报 `does not support reasoning effort "medium"`。
4. 子代理落盘后，你按第四节自检 + 第五节落盘与机器校验走一遍。**先清两件事**：正文里的 `〔待定：…〕`（它没敢编，做对了，你来补表）与 `unlisted-number`（它自己编了数，改回表内值或补进 `facts.md`），再谈文笔。不通过就带具体证据（第几段、违反哪条）让它改该段，最多两轮。
5. 两轮仍不过：你自己改到过，并在末尾注释记一行「本章由 <模型> 起草，主代理返工 N 处」。
6. 汇报时写清是谁写的、你改了哪几处。用户有权知道哪一章换了笔。

边界：子代理只负责把细纲写成正文。**不许它改 bible、不许动 `PROJECT.md`、不许碰别的章**，越界就作废重来。

### L2 手动代笔（默认关，用户开口才开）

产出两件东西到 `novel-project/reviews/draft-brief-ch-YYY/`：

- `prompt.md`：整段可粘贴——设定摘要、本章细纲、硬约束、输出格式、自检五项。写给「看不到这个项目的模型」看，所以路径要换成纯文本内容。
- `context.md`：给支持上传附件的工具当附件——`style.md` 相关节、出场人物小传、上一章最后 300 字、`context-pack.mjs` 的输出（伏笔原句那一节必须带，跨几十章的物象全靠它）。

用户回填后（贴进对话，或自己写进 `chapters/vol-XX/ch-YYY.md`），**先落盘再校验**：路径对不对、有没有把解释性文字一起贴进来、字数是否在区间。机器校验不过就退回，**这一章不计入章数**，也不更新累计字数。

## 一、开写前必读（顺序固定）

1. `read novel-project/bible/style.md`：叙事视角、句法、对话规则、**第八节禁忌清单**、第九节样段——样段读两遍，用它的语感定调。
2. `read novel-project/outline/vol-XX/ch-YYY.md`：本章细纲全部九节，尤其冲突五段与章末钩子。
3. `read` 本章每个出场人物的 `bible/characters/<name>.md`：只读「执念」「说话方式」「压力下的反应」三节。
4. `read novel-project/bible/timeline.md`：本章对应行的故事时间、地点、上一章留下的伤势与约定。
5. `read` 上一章正文最后 300 字：接住语气与钩子。
6. `read novel-project/bible/digest.md`：**最近 3 章**的摘要行，加上按细纲里 F 编号 `grep` 出来的旧行。这本书已经写了三十章，你不会重读三十章正文；这五行就是你的第二层记忆。
7. `read novel-project/bible/facts.md`：本章会用到的度量、账目、纪年、路程口径。表里没有的先补进来，**不许临场编数**——数字是代笔最容易各编一套、读者最容易抓错的地方。
8. 读不到任何一项 → 先补（回 `novel-bible` 或 `novel-detailed-outline`），不要凭印象开写。

## 二、开写前的三行小卡

写进文件开头的草稿注释，写完删掉：

- 本章视角人物：谁的眼睛在看。
- 本章发生的一件事：一句话，含「谁想要什么、被什么挡住」。
- 本章结束时读者的情绪或疑问：一句话。

对照细纲，不一致先停：要么细纲过时，要么理解偏了。

## 三、操作步骤：写作规则（按优先级）

1. **场景目标明确**：每场戏开头三句内让读者知道谁想要什么。没有目标的场景不写。
2. **具体代替形容**：用动作、感官、器物承担情绪。「她很悲伤」改成她做了什么、看见什么、手上攥着什么。每章至少 3 个可触摸的物象。
3. **对话有潜台词**：人物不直说目的；关键对话至少一处「说的和想的不一样」。
4. **说话符合各自习惯**：句长、用词、口头禅、回避话题按小传。不同人物的台词不能互换。
5. **不写总结式抒情与万能金句**：段末不升华，不替读者总结意义，不让角色替作者讲道理。让画面自己说话。
6. **章末落在钩子上**：最后一句是动作、画面或没答完的话；不写「欲知后事如何」。
7. **不擅自新增重大设定**：新能力、新组织、新规则先停，问用户；小物件、路人可以即兴，但记进末尾注释，等这一章收尾时写进设定库。
8. **节奏**：单章 2–4 场戏；高压场景后给一个不超过 200 字的喘息段，不另起一章。
9. **视角纪律**：限知视角不写视角人物不可能知道的事；一章内视角切换不超过 2 次，规则以 `style.md` 为准。
10. **对话提示语克制**：「说」为主，少用「冷笑道」「淡淡道」叠用；动作替代情绪副词。

## 四、写完自检（逐项过，不跳）

- [ ] **与细纲一致**：本章功能、冲突五段、章末钩子都落地；有偏离就写清是有意为之，并记原因。
- [ ] **人物不 OOC**：每个重要选择能回溯到执念与本章处境；说话方式与小传一致。
- [ ] **时间/地点/伤势接得上**：对照 `timeline.md`，没有瞬移、没有伤一夜就好、没有同一晚出现在两地。
- [ ] **重复用词**：同一段不重复同一个形容词或动作；口头禅每章不超过 2 次，用 `grep -c` 统计。
- [ ] **对话区分度**：遮住提示语，能否分辨谁在说；不能就按说话人清单改。
- [ ] **章末钩子成立**：删掉最后一句，本章是否变平；不变说明钩子无效。
- [ ] **字数**在 2000–4000 区间（或 `PROJECT.md` 指定值）。
- [ ] **模板化表达**：没有排比堆砌、每段对仗、空泛形容词、角色讲道理。
- [ ] **没有过度解释**：情绪只给一个载体，不补结果、不补旁人反应；段末那句若是解释，删掉再读一遍。
- [ ] **一段一信息**：没有「动作＋结果＋旁人反应」三连；长句拆短时信息不跟着丢。
- [ ] **禁忌清单**逐条对照 `style.md` 第八节。

超过 2 项不过 → 先改再交，不要把问题留给用户发现。

## 五、落盘与末尾注释

路径：`novel-project/chapters/vol-XX/ch-YYY.md`，章号与细纲一致。

```markdown
# 第 N 章 标题

正文……

<!--
本章新增事实：
- 人物：新出场 / 状态变化（谁受伤、谁知道了什么、谁欠了人情）
- 时间地点：故事时间推进到哪、地点变化、路程与天气
- 伏笔：埋设 F0xx / 回收 F0xx
待入 bible：
- timeline：第 N 日 …
- foreshadowing：F0xx 状态改已回收
- knowledge-*：主角新知道 …
- characters：<name> 首次出场 / 状态改受伤
-->
```

注释是给下一章与 quick check 的账本：**只写事实与待办，不写剧情摘要**。没有新增就写「无」。

更新 `novel-project/PROJECT.md`：当前章、累计字数、本章状态（待确认 / 已确认 / 待改）。

再往 `novel-project/bible/digest.md` 追加一行（四列写法见模板）——**不写这一行，下一章就接不住你**：

```markdown
| N | 第 N 日夜 | 谁想要什么、被什么挡住、结果如何（≤40 字） | 沈砚：从 X 到 Y | 埋 F006；收 F001 |
```

本章没有状态变化写「—」，没有伏笔写「—」。改了旧章就回去改对应行，行尾加「（改）」。

顺手把这一章的**故事线强度改成实测值**（`bible/plot-map.md` 的「故事线强度」表里，本章那一行的各条线），再跑一次同步与重画：

```bash
node "<技能 Base directory>/../novel-graph/tools/graph-sync.mjs" --project novel-project
node "<技能 Base directory>/../novel-graph/tools/render-graph.mjs" --project novel-project
```

sync 会把新出场的人物、新形成的关系补进关系图；重画只是刷新 `.svg`。**图不跟着章节走，写到第 20 章时它还停在第一章**，这就是返工。

最后给这一章存一版——**这是改稿核对的锚点**。不存的话，作者下次手改完，脚本分不清哪些是他改的、哪些是你原先写的：

```bash
node "<技能 Base directory>/tools/reconcile-chapter.mjs" <章号> --project novel-project --archive
```

老项目第一次开用也这么补：`--all` 会列出哪些章还没有存档，逐章 `--archive` 一遍。

### 落盘后的机器校验（三条通道都要跑）

```bash
node "<技能 Base directory>/tools/check-chapter.mjs" \
  novel-project/chapters/vol-XX/ch-YYY.md --min 2000 --max 4000 --bible novel-project/bible
```

退出码 1 ＝ 还没写完：error 清零，warn 逐条看一眼（人名误报很常见，看一眼就过）。

三个脚本分工不同，各管一段，不要互相替代：

| 脚本 | 管什么 | 什么时候跑 |
| --- | --- | --- |
| `context-pack.mjs` | **开写前读到什么**：细纲点名的伏笔原句、最近三章摘要、上一章末尾、到期未收的伏笔 | 第一节之前 |
| `check-chapter.mjs` | **写完对不对**：字数、占位符、注释闭合、小卡残留、未登记数字、`〔待定〕` | 落盘之后 |
| `reconcile-chapter.mjs` | **改了什么**：与存档比，列出改动的段、新出现的数字/伏笔/人物，并给建议级别；级别 2/3 会挂一条「设定待更新」 | 落盘存档时、作者改稿后、每章开写前体检 |

`check-chapter.mjs` 只管「不需要判断力的事」：字数区间、代码围栏残留、模板占位符、注释不闭合、三行小卡没删、末尾账本缺失、疑似未登记人名、单段超 500 字、`〔待定〕` 未清、数字不在 `facts.md`。最后两项是给代笔用的：代笔自编数字几乎必犯，且肉眼最难发现。

跑不起来（没 node、路径不对）就手工替代，**不许跳过**：

```bash
f=novel-project/chapters/vol-XX/ch-YYY.md
wc -m "$f"                                    # 字数（再减去注释里的字）
grep -nE '本章视角人物|本章发生的一件事' "$f"   # 应无输出
grep -c '<!--' "$f"; grep -c -- '-->' "$f"    # 两个数相等
```

围栏残留与模板占位符这两项，用编辑器的搜索各搜一次（三个反引号、两个左花括号），比背 grep 语法快。

## 六、用户交互点

交稿后只问 1–2 个问题（`ask_user_question`，给选项与推荐）：

1. 「这章节奏合适吗？」选项：合适，继续下一章（推荐）/ 前半慢后半赶 / 整体太赶，要加一场戏。
2. 「本章戏份最重的人物，语气对吗？」选项：对 / 太文或太糙 / 不像他，我贴一句想要的。

再给 2–3 个**可选**修改方向，不强制：把某段的解释改成动作、删掉结尾抒情、给对手补一句台词、把某场戏提前。

用户要改时：按批注逐条改，保留其余段落；除非用户明确说「重写」，不要整章重来。改完只汇报改了哪几处，不重复贴全文。用户说「先放着」：状态记「待改」，停写下一章。

## 七、触发检查（主动，不等用户）

- 连续写完 1–3 章：**主动加载 `novel-quick-check`**，把这几章与末尾注释里「还没写进设定库」的条目交给它。不要等用户发现逻辑问题。
- 一卷写完：更新 `PROJECT.md` 后进入 `novel-mid-check`，不直接开下一卷。
- 出现以下信号立刻停写并检查：新人物没说清动机就死了、伏笔到期没回收、主角能力突然变强、时间线跨度过大、同一物件前后描写矛盾。
- quick check 发现问题：按它的结论改，不在正文里静默打补丁。

## 八、产出文件

- `novel-project/chapters/vol-XX/ch-YYY.md`（含末尾 HTML 注释）。
- `novel-project/PROJECT.md`：当前章、累计字数、本章状态、还没写进设定库的条目。
- 新增人物/伏笔/时间点：在汇报里列成待办，提醒用户 quick check 时补进设定库；**不擅自改 bible 既有条目**，除非用户同意。

## 九、质量自检清单（交稿前最后一遍）

- [ ] 细纲九节都落地，钩子没丢
- [ ] 字数、视角、人称与 `style.md` 一致
- [ ] 至少 3 个具体物象、1 处潜台词对话
- [ ] 第四节发现的问题全部改完
- [ ] 文件末尾注释齐全，「还没写进设定库」的条目不漏
- [ ] 正文里的数字/度量都能在 `bible/facts.md` 找到出处，没有 `〔待定〕` 残留
- [ ] `PROJECT.md` 已更新
- [ ] 机器校验跑过：error 清零，warn 逐条看过（人名误报要说明是误报）
- [ ] 已存档（`reconcile-chapter.mjs <章号> --archive`），级别 2/3 的话「设定待更新」还挂着
- [ ] 代笔章节：末尾注释写明起草模型与返工处数，汇报里也说了
- [ ] 没有把草稿注释、提纲句子留在正文里

## 十、门禁

用户确认本章后：更新 `PROJECT.md`（本章状态改「已确认」、当前章 +1），再写下一章。**未确认不写下一章。**
一卷写完：`PROJECT.md` 记录卷末状态，加载 `novel-mid-check`。

## 十一、失败 / 回退分支

- **写不出来**（细纲没问题但没语感）：先写 300 字样段找语感，或换一个场景切入点重写开头；不硬凑字数。
- **像大纲扩写**（全是事件没有场景）：停，回细纲补「3 个物象 + 一场对话」，再重写该场。
- **与 bible 冲突**：按 `novel-bible` 的冲突三步处理——停写、列证据、用户决定，不擅自改设定。
- **用户要大幅改文风**：回阶段 2 更新 `style.md`，从下一章应用；已写章是否重写由用户决定。
- **字数严重超标**（>5000）：先删解释性段落与重复动作，不删冲突与钩子；仍超就拆成两章，先问用户。
- **写盘失败或目录不存在**：`bash mkdir -p novel-project/chapters/vol-XX` 后重试；不写到 `outline/` 或根目录，不覆盖已确认章节。
- **代笔模型不可用**（路由没放行、返回空、中途超时）：改走 L3 自己写，**不拿半截稿凑数**；把模型名与报错原文记进末尾注释，下一章不再自动试同一条路，等用户决定换模型还是换通道。
- **报 `does not support reasoning effort`**：这是参数问题不是路由问题。去掉 `reasoning_effort` 重试一次，仍失败再走 L3。别把这条和「路由没放行」混为一谈，否则会误报「Host 没配好」。
- **代笔自己编了数字/度量**（`unlisted-number` 报一串）：不要顺手续写。先判断是「表里漏登记」还是「它编错了」——前者补 `facts.md` 并按表回填正文，后者改回表内值；两处以上且互相矛盾，说明这份细纲给的信息不够，回 `novel-detailed-outline` 补「本章关键数字与算式」。
- **代笔稿文风跑偏**（像另一个作者）：先看是不是没把 `style.md` 第九节样段给它；补上样段再试一轮，仍偏就回 L3，并在汇报里说明「这个模型不适合这本书的语感」。

## 十二、改稿回流（作者自己改了正文之后）

设定库是单向记账的：它只在「正文写完」那一刻记一次。作者后来手改了正文，设定库不会自己知道。这一节补这个洞——**改稿是独立事件，不是「又写了一遍」**。

改稿在系统里拆成两件事，别混：

| 概念 | 是什么 | 谁推进 |
| --- | --- | --- |
| **存档**（`.versions/` + `manifest.json`） | 最近一版被核对过的正文副本，用来算「这次改了什么」 | 保存正文时自动前进，不用手点 |
| **待更新设定**（`pending`） | 一笔债：正文改到级别 2/3，设定库还没跟上 | 改完 `bible/` 后清掉（面板「设定已更新」，或 `--archive`） |

分开记的理由：如果「存档」同时充当「已经处理完」的标记，作者一点存档，债务就凭空消失了；面板没法验证你到底改没改设定库。

### 1. 存档是什么

正文每保存一次，脚本把新稿存进 `novel-project/chapters/.versions/vol-XX/ch-YYY.vN.md`，并在 `.versions/manifest.json` 记下 hash 与字数。**改稿判定全靠它**，别手删。

`.versions/` 自带 `.gitignore`：正文副本默认不进版本库，`manifest.json` 留（只存 hash 与字数，换台机器也认得出哪一章被改过）。

没有存档的老章先跑一次 `reconcile-chapter.mjs <章号> --archive`（退出码 3 就是在说这个）。

Web GUI 侧栏的「小说助手」面板读的是同一份 manifest：点开一章改正文、`⌘S` 保存，当场出级别与清单；设定库改完按「设定已更新」清债。保存之后改动就成了「新常态」，想再看那次改了什么，按「看上次改了什么」——旧版还留在 `.versions/` 里，没有丢。**面板只做同一套动作，不另立规则**——同一章在面板里核对和在对话里跑脚本，结果必须一样；两边不一致时以脚本为准，那是唯一实现（`lib/reconcile.js`）。

### 2. 三个入口

- 作者说「我改了第 N 章」→ 跑 `<章号>`，拿清单。
- 每章开写前 → 跑 `--all` 体检一次；有「改过、还没核对」的章，先核对再动笔，否则新章会建在旧账本上；有「设定库要跟上」的章，先处理清单。
- 你自己回改旧章（按用户批注）→ 改完同样跑 `<章号>`；级别 1 到此为止，级别 2/3 改完设定库再 `--archive`。
- 想回看「上次保存到底改了什么」→ 跑 `<章号> --since <上一版号>`（面板上是「看上次改了什么」）。它拿旧存档和当前稿比，不前进存档、不挂标记，纯回顾。

### 3. 清单长什么样

脚本产出 `novel-project/reviews/draft-edits/ch-YYY.md`：改动的段（原句/现句对照）、字数与段数变化、新出现与不再出现的数字/伏笔编号/人物/台词，以及这一章现有的 digest 行。终端同时给一句「建议级别 N」。

### 4. 三级判定（脚本只数信号，级别由你判）

有一条例外要先知道：**改回 `facts.md` 里记的值不算事实改动**。把误写的「七尺一寸」改回「七尺二寸」，脚本会认出这是收口，报级别 1、不挂债——别在这上面绕一圈去改设定库。

| 级别 | 判断标准 | 要做什么 |
| --- | --- | --- |
| 1 措辞级 | 换比喻、删形容词、调句序；人物、事件、数字、台词归属都没变；**或把数字改回 `facts.md` 里记的值** | 设定库不动，改完即完（存档已自动前进） |
| 2 事实级 | 数字/度量变了、器物换了、谁在场或谁说了什么变了 | 逐项核对 `facts.md`、`timeline.md`、`characters/`、`digest.md`；改完再清掉「待更新设定」 |
| 3 结构级 | 事件结果、信息差、伏笔取消或提前、人物动机变了 | **先停**，见下 |

级别 3 的动作顺序（不许跳）：

1. `grep` 后续细纲与已写正文，找出依赖旧写法的章与段，列成「失效清单」。
2. 用 `ask_user_question` 把清单与两个方案给用户：改后续（列出要改哪些章）、或把改动收回去。**不替用户决定，也不静默改 `outline/` 与细纲。**
3. 用户确认后才动大纲/细纲，并在 `PROJECT.md` 决策日志记「改了什么、为什么、影响哪几章」。

### 5. 只改了注释也算改动

脚本会识别「正文没动、只有末尾注释变了」：那是记账动作，不是改稿——确认注释里的条目都落到了 `bible/`，这一章就算完；脚本不会为它挂「待更新设定」。

### 6. 三条硬规矩

- 清单没处理完 = 没改完。`--all` 里那条「设定库要跟上」就是提醒：级别 2/3 的清单不处理，越攒越难对。
- 级别 3 不问用户就改大纲，等于替用户做了创作决定——这是本项目最不能碰的一条。
- 核对清单是证据，不是结论；结论写在 `PROJECT.md` 决策日志里。
