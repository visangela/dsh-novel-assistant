# 阶段 5 · 设定库建档与维护

目标：让 `bible/` 成为全书的**唯一事实来源**。阶段 1–3 的设定散在 `architecture.md`、`outline.md`、人物小传和对话里，本阶段把它们收成七份账本：时间线、伏笔、读者已知、主角已知、人物索引、硬事实表，外加一份随章增长的章节摘要。**建档不是抄一遍，是提取约束**——只登记会限制后续写法的东西。

## 一、前置检查（2 分钟）

1. `read novel-project/PROJECT.md`：当前阶段必须是 5；阶段 4 审核结论是「采纳」。若仍是「待改/驳回」，先回阶段 4，不建档。
2. `glob novel-project/bible/**/*.md`：七份表是否都在。缺表就从 `skills/novel-setup/templates/bible/` 复制；已存在则**只做增量与校正，不清空旧行**。
3. `read bible/architecture.md`、`bible/outline.md`：确认有主线、分卷表、章节关键设定表、结局。缺结局就先回阶段 3。
4. `read bible/characters/_index.md` 与主要人物小传：至少 3 个核心人物有「执念」「说话方式」两节。
5. 检查 `bible/outline.md` 的「埋设 / 回收」列是否有内容。空列不要自己编伏笔，在汇报里标为「大纲信息不足」。

## 二、操作步骤

用 `todo_write` 列四项：抽时间线 → 抽伏笔 → 建两张信息表 → 建人物索引。

### 1. 抽取时间线（`timeline.md`）

数据源：分卷表的「核心事件」、章节关键设定、人物小传的「改变他的那件事」。按模板六列填：故事时间 / 章节 / 事件 / 涉及人物 / 地点 / 后续影响。

- 时间先相对后绝对：「第 1 日」「三日后」「同年秋」；同一天多个事件写「第 1 日 · 上午」「第 1 日 · 夜」。
- 一章跨日就拆成多行；两章同一时间就并列两行，让「同时发生」可见。
- 「后续影响」写它改变了什么：伤势、约定、失去的物件、暴露的身份、欠下的人情。**不写剧情复述。**
- 只登记会约束后文的事件：受伤、赶路、约定、得到/失去关键物、身份暴露、关系破裂。吃饭睡觉不登记。
- 向用户说明一句：「时间线记的是约束，不是摘要。」

### 2. 抽取伏笔（`foreshadowing.md`）

编号 `F001` 起，三位数，**只增不销、不跳号复用**。按模板填：编号 / 伏笔内容 / 埋设章 / 指向的真相 / 预定回收章 / 状态 / 备注。

- 一条伏笔 = 一个读者看见但尚未理解的具体物象或信息。「主角以后会变强」不算伏笔，除非有具体载体（半块玉、一句反常的话）。
- 埋设章必须是大纲里真实存在的章；只有构想、正文未写的，备注写「预埋」。
- 预定回收章可写区间（第 12–15 章），但必须给一个**最迟章**。
- 状态只允许三种：`未回收`、`已回收`、`逾期`。需要「部分回收」就拆成两条，不要发明第四种状态。
- 密度参考：短篇 8–15 条；长篇每 10 万字 12–20 条。超过 25 条提醒用户「回收压力大，建议合并」。

### 3. 建读者/主角两张信息表

- `knowledge-reader.md`：读者何时、通过什么方式知道什么，按章顺序追加。
- `knowledge-protagonist.md`：主角何时知道、是否相信。多出的「是否相信」列是关键：**知道但不信**是后续反转的燃料。
- 一条信息写一句话，写「信息」不写「事件」。同一条信息两边的知道章不同，就各占一行。

**两表之差 = 悬念或戏剧反讽**。建档时必须显式标出每处差值的类型与用法：

| 情形 | 读者 | 主角 | 效果 | 用法 |
| --- | --- | --- | --- | --- |
| 读者第 3 章看见凶手袖口有血，主角第 9 章才知道 | 早知 | 后知 | 戏剧反讽 | 每次凶手在场，读者替主角紧张 |
| 主角第 5 章读到密信，读者第 12 章才看到内容 | 后知 | 早知 | 悬念 | 读者追着问「信里到底写了什么」 |
| 读者第 7 章知道配角是卧底，主角第 20 章仍信任他 | 早知 | 不知 | 戏剧反讽 + 倒计时 | 两人同框自带压力，读者数着日子等揭穿 |

规则：一处差值只服务一个效果。同一章里既让读者知道、又让主角立刻知道，差值归零，前面的铺垫白费。

### 4. 建人物库索引（`characters/_index.md`）

先有小传，再有索引行：用 `_template.md` 补全 `characters/<拼音或英文名>.md`，再到 `_index.md` 登记姓名 / 身份 / 阵营 / 与主角关系 / 首次出场 / 当前状态 / 小传路径。

- 「首次出场」写正文或大纲预定的章号，不写建档日期。
- 当前状态只允许：存活 / 受伤 / 失踪 / 死亡。受伤要写部位与对行动的影响（写进小传或备注）。
- 有名字但暂无关键戏的配角，至少三行小传：身份、与主角关系、一个可复用的记忆点。否则后面容易写重名、写串性格。
- 用 `grep` 查近似名（「林晚」「林婉儿」），提醒用户合并或加区分标志。

### 5. 建硬事实表（`facts.md`）

这张表管的是**代笔最容易自编、读者最容易抓错**的一类东西：数字。同一场戏里「空船吃水三尺一寸、每百石沉一寸四分」这种数，大纲不会写，风格指导书也不管，谁写谁编——第一章编一套，第八章再提就打架。

收集范围（只收会进正文的）：

- **度量换算**：尺寸、斤两、石斗、里步、时间刻度。全书一套，不许换口径。
- **账目与价格**：银钱、米价、工钱、损耗率、利钱。写清名义（正耗 / 加耗 / 折色）。
- **纪年与日期**：年号、节气、干支、闰月、每天几个时辰怎么称呼。
- **地理与路程**：两地几天路程、走水路还是陆路、闸口与码头的位置关系。
- **器物与规格**：船型料数、兵器尺寸、官印形制、算盘档数。
- **身份与官制**：官职全称、上下级关系、称呼规矩。

写法：

- 一行一条，`条目 / 值 / 出处 / 备注`。出处写首次出现的章（未写的写「细纲」），别写建档日期。
- **能算出中间结果的值，要把算法也写进备注**（例：`吃水 = 空船吃水 + 石数 ÷ 100 × 每百石下沉`）。代笔照着算，才不会各编各的。
- 冲突处理：以正文为准还是以表为准，按第五节走用户确认；**不改值、不清行**，在备注与「变更记录」留痕。

发一句话给用户：「这张表锁的是数字，不是文笔——表外的比喻和细节，代笔随便写。」

### 6. 建章节摘要（`digest.md`，先建表头）

这本书越写越长之后，**没有第二层记忆**：写第 40 章时，前面的正文没人重读，伏笔表又只有一行摘要。这一步先立表，阶段 7 每写完一章追加一行。

- 建档时只建表头与写法说明，**不要预写剧情摘要**（章节还没写，写了就是编）。
- 表头五列：章 / 故事时间 / 一句话剧情 / 谁的状态变了 / 埋·收。写法照模板里那四条。
- 一句话剧情必须含「谁想要什么、被什么挡住、结果如何」；状态变化写「谁：从 X 到 Y」；埋收看编号。
- 它和伏笔表的分工：伏笔表管**这条线**（内容、真相、预定回收章），摘要管**这一章发生了什么**。查一条线经过哪几章，`grep "F001" bible/digest.md`；查第 N 章前后发生了什么，看最近三行。

写正文时，`novel-draft` 会用 `tools/context-pack.mjs` 把「最近三章摘要 + 细纲点名的伏笔原句」打成一个包，不重读全书。

## 三、一致性查询配方（开写前直接用）

`grep` 工具按 pattern + path 查；需要跨文件统计时用 `bash`：

```bash
# 某人出现在哪些章、被谁提到
grep -rn "沈砚" novel-project/chapters novel-project/outline

# 一条伏笔的全部痕迹（编号必须全局唯一）
grep -rn "F007" novel-project/

# 时间词：核对同一天没被写成两天
grep -rnE "次日|翌日|当夜|三日后|半月后" novel-project/chapters/vol-01/

# 能力使用：核对没超上限、没忘代价
grep -rn "引气\|御物" novel-project/chapters/

# 口头禅滥用计数（单章超过 2 次就减）
grep -c "罢了" novel-project/chapters/vol-01/ch-003.md
```

补充：`glob novel-project/chapters/vol-01/*.md` 确认章号连续；`grep -rn "TODO\|待定" novel-project/bible` 清空占位符。

## 四、维护协议（每写完一章必做）

> 第 0 步：新人物登记进 `characters/_index.md`、并在其小传里补「## 关系网」表之后，跑一次 `novel-graph/tools/graph-sync.mjs`，让人物与关系自动进图谱；否则两张图会停在开书时的样子。

顺序固定，先改 bible 再写下一章，不许「攒几章一起补」：

1. `timeline.md` 追加本章事件与时间跨度；若与旧行冲突，当场标出。
2. `foreshadowing.md` 新增本章埋设；本章回收的把状态改 `已回收`，备注补实际回收章。
3. 两张信息表追加本章新知；有新差值就标类型。
4. `characters/_index.md` 更新首次出场与当前状态；新人物先建小传再登记。
5. `facts.md` 收本章新出现的数字、度量、价格、路程；正文与表冲突的，先停写再按第五节处理。
6. `digest.md` 追加本章一行（四列表格，写法见模板）；改了旧章就回去改对应行，行尾加「（改）」。
7. `PROJECT.md` 决策日志记一行「第 N 章已记进设定库」。
8. 拿到 `reviews/draft-edits/ch-YYY.md`（作者手改过正文）：按清单标的级别处理——级别 1 不动表；级别 2 逐条核对 `facts.md` / `timeline.md` / `characters/` / `digest.md`；级别 3 先停，按第五节走（列失效章 → 用户决定 → 才动大纲与细纲）。处理完让主代理跑 `reconcile-chapter.mjs <章号> --archive`：这一步会清掉那章挂着的「设定待更新」标记。

硬规则：

- 新增人物：小传 → 索引 → 时间线补首次出场，三步缺一不可。
- 伏笔到期未回收：状态改 `逾期`，**不许偷偷修改预定回收章**。要改就记录原因、影响章，交用户确认。
- 时间线冲突：以 bible 为准改正文；若是 bible 本身错了，改 bible 并在 `reviews/bible-check-*.md` 记「修正 / 原因 / 影响章」。
- 每 5 章做一次抽查：人名、伏笔号、时间词各一次 `grep`。
- 改稿按级别记进设定库：脚本给的是信号提示，级别由人判；**级别 3 不许静默改大纲或细纲**。
- `chapters/.versions/` 与 `manifest.json` 是改稿核对的唯一锚点，不许删；删了下次核对会把两次改动混成一批。

## 五、冲突处理（正文与 bible 打架时三步）

1. **停写**：不继续写、不顺手改正文。记下文件与行号。
2. **列证据**：正文写法、bible 条目、大纲条目三处并列，标出谁先出现、影响哪些章/伏笔/人物。
3. **用户决定**，给方案与代价：
   - 改正文（推荐，bible 已确认且影响面小时）：列出要改的句子与后续衔接。
   - 改设定：评估影响面（章节、伏笔编号、人物关系、时间线行），按「大纲 → 细纲 → 设定库 → 正文」顺序联动改。
   - 第三条路：两者都能成立时，把它变成设定（口误其实是谎言/失忆），但先确认不破坏人物一致性。

改完在 `PROJECT.md` 决策日志记一行，写清「改了什么、为什么、影响哪些文件」。

## 六、用户交互点

建档完成后一次性汇报，不超过 12 行：

- 时间线 10 行摘要（表格：故事时间 / 章节 / 事件，只挑关键行）；
- 伏笔总数，其中未回收 / 逾期各几条；
- 人物数（主要 / 有名有姓）；
- 风险 2–3 条（如「第 8 章和第 11 章都写主角在城南，时间只差一天」）。

然后 `ask_user_question` 问 1–3 个，带选项与推荐：

1. 时间线起点与跨度对吗？选项：对 / 改成以某事件为第 1 日 / 我补充。
2. 伏笔密度合适吗？选项：保持 / 减 3 条（超过 25 条时推荐）/ 加 2 条。
3. 信息差用法按「先反讽、后悬念」吗？选项：按建议 / 我想让读者更早知道 / 让主角更早知道。

## 七、产出文件

- `novel-project/bible/timeline.md`：行数不少于大纲章数的 0.6 倍。
- `novel-project/bible/foreshadowing.md`：`F001…` 连续编号。
- `novel-project/bible/knowledge-reader.md`、`knowledge-protagonist.md`。
- `novel-project/bible/characters/_index.md` 与新增小传。
- `novel-project/bible/facts.md`：至少覆盖本章用到的度量与账目口径。
- `novel-project/bible/digest.md`：表头就位；已写章节每章一行，行号与 `chapters/` 里的章号一致。
- `novel-project/reviews/bible-check-v1.md`：三段——缺失项、矛盾项、待确认项，每条带文件与行号。

## 八、质量自检清单

- [ ] 七份表都在，表头与模板一致，没有未替换的 `{{...}}` 或空占位
- [ ] `digest.md` 的行数与已完成章数一致，埋收编号都能在 `foreshadowing.md` 里查到
- [ ] `facts.md` 里每个会进正文的数字都有值，能算出中间结果的写了算法
- [ ] 时间线每行都有故事时间与章节，不出现「某日」「后来」
- [ ] 每条伏笔有编号、埋设章、指向真相、最迟回收章、三态之一
- [ ] 没有两条伏笔指向同一个真相（有就合并，或改指向）
- [ ] 两张信息表各至少 5 条，标出 2 处以上差值并注明类型
- [ ] 每个出场人物在索引有一行，小传路径真实存在（`glob` 抽查）
- [ ] 无重名与近似名
- [ ] 与 `outline.md` 的章节关键设定没有直接冲突
- [ ] `reviews/bible-check-v1.md` 已写，问题可执行

## 九、门禁

给用户看汇报与 1–3 个确认问题。用户确认「设定库完整」后：更新 `novel-project/PROJECT.md`（当前阶段改 6、阶段记录加一行、划掉已解决的待确认项），加载 `novel-detailed-outline`。**未确认不写细纲。**

## 十、失败 / 回退分支

- **大纲信息不足**（章节表空、结局未定）：不硬建。给两个选择：先回阶段 3 补大纲（推荐），或只建「最小设定集」（主线 + 前 10 章）并在 `PROJECT.md` 标「设定库草稿」。
- **人物小传缺失**：先补 3 个核心人物，其余在 `bible-check-v1.md` 列「待补清单」，不阻塞细纲。
- **已有正文与 bible 大范围冲突**：不要批量改正文。先出冲突清单，用户选「以正文为准回填 bible」还是「以 bible 为准修正文」。
- **用户不想维护七份表**：降级为四份（时间线、伏笔、人物索引、章节摘要），`facts.md` 只留「度量与账目」一片，在 `PROJECT.md` 标记，quick check 时补齐。**摘要不能降**——它是长篇唯一的第二层记忆。
- **写盘失败或路径不存在**：用 `bash mkdir -p novel-project/bible/characters` 建目录后重试；大文件分节 `edit`，不要整文件覆盖。

确认后更新 `novel-project/PROJECT.md`，加载 `novel-detailed-outline`。
